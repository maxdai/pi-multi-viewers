# calculator.py 可读性视角分析

## 1. 命名层的问题（最严重）

### 1.1 `summarize(items)` —— 命名欺骗

这是整个文件里**可读性最大的硬伤**。

`summarize` 在英文里暗示"汇总、摘要、聚合"，调用方读到这个名字时，脑中浮现的是 `total` / `avg` / `max` / `distribution` / `summary statistics` 这类**带信息密度的聚合**。但函数体里做的事只有一件：`total = 0; for i in items: total = add(total, i)`——也就是 `sum`。

这是个**意图-实现错配**：
- 名字承诺的是"摘要"，交付的是"求和"
- 调用方为了确认自己理解的没错，得**跳进函数体读一遍**才能消除歧义
- 一旦日后有人在 `summarize` 里加了 `count` / `mean`，调用方代码不需要任何修改就会被静默改变语义——这是隐藏的耦合风险

**修法**：要么改名为 `sum_items` / `total`，要么把函数体真正做成 summary（带 mean/count/std 之类）。单纯保留 `summarize` 然后 `return total` 是不可接受的。

### 1.2 `add(a, b)` —— 零信息量的名字

`add(a, b): return a + b` 这个函数提供了**负的语义增量**：
- 比 `a + b` 长了 8 个字符
- 名字 `add` 与 `+` 操作符字面重复，读者无法从中获得任何 `+` 给不出的信息
- 它**强迫读者跳进去看一行**才能确认"哦，就是加法"

这是教科书式的**负向抽象**：一层包装、零价值、纯阅读税。在 `summarize` 里用 `add` 而不是 `+=`，让两层间接（summarize → add → +）都只为了一次加法——每一层都迫使读者心算"这一层在干嘛"，答案是"啥也没干"。

### 1.3 `fib(n)` —— 命名 OK，但契约不显

`fib` 这个名字清晰，递归实现也是斐波那契数学定义的**直接翻译**——在"表达数学定义"这个维度上朴素递归反而最可读。但问题在于：
- 没有说明 `n` 能取多大（实际上到 ~35 就卡顿，到 1000 直接 `RecursionError`）
- 没有说明负数会怎样（会无限递归，直到栈溢出）
- 没有 docstring 把"返回斐波那契数列第 n 项（0-indexed）"这个**契约**写出来

调用方读签名 `fib(n)` 完全无法预判失败模式。

## 2. 抽象层的问题

### 2.1 间接链 `summarize → add → +`

把加法拆成三层，每一层都不携带语义：
- `summarize`: 本应是聚合
- `add`: 是个被滥用的薄包装
- `+`: 才是真正的运算

这种"为拆而拆"的结构让**调试栈变长**、**阅读路径变深**，却没有获得任何复用收益（`add` 在文件里只有一个调用方）。

### 2.2 模块边界

三个函数平铺在同一个模块，模块叫 `calculator`——但里面只有一个算术工具、一个数列工具、一个聚合工具，**它们之间没有共同抽象**。这不算结构问题（13 行代码不值得拆模块），但**当函数数到 10+ 时**，如果没有分组（基础运算 / 数列 / 聚合），可读性会迅速恶化。当前规模合理，但需要在扩展时警惕。

## 3. 契约层的缺失

整个文件没有：
- 类型注解（`summarize` 期待 `Iterable[int]`？`Iterable[float]`？generator？调用方不知道）
- docstring（每个函数的语义、边界、失败模式全靠读者猜）
- 边界示例（`fib(0)` 返回什么？`fib(1)`？`summarize([])`？）

这三个缺失让**调用方必须在脑里同时维护"代码可能的含义"和"代码可能的失败方式"两个不确定模型**——这是隐藏的心智负担。

## 4. 对 a 的回应

a 的性能分析我基本同意事实部分（`fib` 是指数级、`summarize` 常数因子浪费、`add` 是冗余抽象）。但有几条建议从可读性角度我要**反对或修正**：

### 4.1 反对用 `functools.lru_cache` 修 `fib`

a 把它列为"代码改动最小"的选项，但从可读性看恰恰相反：
- `lru_cache` 引入**隐式状态**（全局缓存、跨调用持久），读者必须查文档/源码才能知道 cache 存在
- 缓存何时失效、线程安全如何、占用多少内存——都是隐形的
- 迭代版本（`a, b = 0, 1; for _ in range(n): a, b = b, a + b`）虽然代码量略多，但**所有状态都在三行局部变量里显式呈现**，读者一眼能验证正确性

如果一定要保留递归形式，至少用**显式手写 memoization**（带 `cache: dict` 参数），而不是 `lru_cache` 这种装饰器魔法——这样意图（"我们要记忆化"）是显式的。

### 4.2 同意用 `sum()` 内建，但理由不同

a 从性能角度建议用 `sum()`，我也同意，但**更重要的理由是命名**：
- 如果整个 `summarize` 就是 `sum`，那它就是个**被错命名的 `sum`**
- 直接在调用方写 `sum(items)` 比 `summarize(items)` 更清楚，**连函数都不用定义**
- 性能收益（内建 C 实现）是顺带的

### 4.3 完全同意移除 `add`

这点 a 的性能和我的可读性两个视角难得地完全一致——`add(a, b)` 没有任何可读性贡献也没有任何性能贡献，纯粹的负向资产。

## 5. 可读性视角的优先级

按 ROI 排：
1. **重命名 `summarize` 或删除它**——消除命名欺骗（最关键）
2. **删除 `add` 或合并调用点**——消除负向抽象
3. **给 `fib` 加 docstring + 迭代化 + 边界说明**——契约显式化
4. **加类型注解**——让契约可静态检查

可读性视角的核心立场是：**当一个名字承诺 X、交付 Y 时，bug 不是性能，而是信任**——后续所有在这个名字上做的修改都会被同样的误解污染。
