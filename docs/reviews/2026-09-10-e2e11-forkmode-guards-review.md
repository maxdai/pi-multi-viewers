## 二、需修复项

### 2.0 结构语义缺陷（三方已裁决修法）

#### P1 `compaction` 模式产物含**重复 compaction 条目**（同一 id 两次）

- **证据**：真实主 session（6975 条 / 9 个 compaction）实测产物 body 3129 条，`c5d43076` 出现在位置 **[0, 805]**；两视角独立复现。
- **机制（经更正）**：正常路径 `kept_idx < comp_idx` **恒成立**（pi `session-manager.js` `appendCompaction(parentId=leafId)` 保证锚在 comp 之前）⇒ `entries[kept_idx:]` 必含原件 ⇒ `[comp] + body` **恒为重复**。prepend 副本**被 last-wins 遮蔽**（pi `buildEntryIndex` 顺序 `set`、后者覆盖前者 → 解析到原件），副本不可达、不参与 replay——"孤立节点"是**不成立的机制描述**（铁律/0001 与可读性/0003 均曾误用，后经核实更正）。
- **实害**：① 产物/声明不一致（违反"最后 compaction + firstKeptEntryId 起的条目"）；② 对**文件顺序**的隐含依赖（last-wins 遮蔽只在原件在后时成立）；③ 对按 first-wins/线性扫描解释产物的消费者的脆弱性。
- **修法（定夺）**：**删除 prepend**——compaction 模式 = `entries[kept_idx:]`；锚失效保持 fail-fast（与"无静默"一致）。不写 fallback、不搬家（"prepend 仅 fallback"在 compaction 模式无 fallback 可依——该表述曾误导两位评审者，meta 论据支持删除）。
- **docstring 措辞**："从 `firstKeptEntryId` 起的条目（含最后一个 compaction 条目本身，位于其自然位置）"。
- **修复动机句**（表述纪律）：引用仓内不变量（"满足 I1（id 唯一）、消除 last-wins 顺序依赖"）——**不写"修复 replay 破坏"**（replay 并未损坏）。

#### P2 `budget` 窗口含 compaction 条目时，pi replay **静默丢弃前缀**（含 preface）

- **证据（复刻 pi replay 探针）**：产物 `[preface, old7, k1, k2, C1, n0..n2]` → 可见 `[C1, n0..n2]`（前缀全丢）。两个形态：
  - (a) 锚被裁掉（`firstKeptEntryId` 不在产物内）→ 前缀全丢；
  - (b) 锚仍在产物内、但产物有锚前条目 → **锚前条目丢失**（场景5：`k0` 丢）。
  - 精确化：**comp 是窗口首条时修复前就已正确**（`ci=0` 不扫描）。触发 ⇔ 窗口含 compaction 且其非窗口首条（"刚压缩完就 fork"）。
- **修法（定夺）**：**窗口内 compaction「规范化移除 + 桥接」**——
  - 移除窗口内**全部** compaction 条目；指向被移除条目的 `parentId` 上溯到第一个非 compaction 祖先（连续 compaction 链亦正确）；上溯出产物 → 链首 `parentId = None`（显式链首，与 preface 同型）；
  - 位置：在**边界对齐之后、preface 注入之前**；流水线整句进 docstring：**`fold → trim → 对齐 → normalize → preface → est`**；
  - **退化守卫**：规范化致 body 为空（窗口仅含 compaction）→ **保留该条**（成为链首，replay 天然全集合可见）；
  - `est`：现有"对最终 body 统一求和"的单一测点自动正确（compaction 条目 `_entry_text` 为空、`_est_tokens` 返 1 → 移除后 est 降 `#removed`，无需恒等断言）；
  - **信息损失边界**：最后一条 comp 摘要已在 preface（"此前压缩摘要"行）；更早的是被滚动摘要覆盖的旧摘要——损失有界。
- **裁决记录**：先前 铁律/0004 提出的"**批量改写锚点**"方案**已撤回**（语义上伪造历史字段；且中间锚仍悬空）。性能/0007/0010 的"改写 0.07ms/0.27ms、est 恒等"测量**对应已撤回机制**——成稿勿并载（性能/0013 亦确认）。

#### 台账缺陷：边界对齐致 `dropped` **双重计数**（独立复现 + 第二破法场景）

- **证据**：`_budget_entries` 的 `dropped` 在边界对齐循环**之前**绑定（`meeting_fs.py` `dropped, kept = folded[:cut], folded[cut:]`），循环只改 `cut` 不回写 `dropped` → 回扩条目**同时留在 kept 与 dropped**。
  - 场景 B（源 3 条：big / a1-toolCall / r1-toolResult，`keep_tokens=5`）：kept=2 + dropped=2 = **4 ≠ 3**（a1 双重计数）；
  - 场景 C（源 2 条：big / 孤儿 r2）：kept=2 + dropped=1 = **3 ≠ 2**（big 从 dropped 但在 kept）；
  - 真实源今日回扩 0 次 → **潜在态**（结构触发的低频路径，与 P2 同型）。
- **修法（最小）**：

  ```python
  orphans = []                     # 新增：对齐中真正丢弃的孤儿（cut==0 分支）
  while kept and (kept[0].get("message") or {}).get("role") == "toolResult":
      if cut > 0:
          cut -= 1
          kept = folded[cut:]
      else:
          orphans.append(kept[0])
          kept = kept[1:]
  dropped = folded[:cut] + orphans # 循环后重算（消除 stale binding）
  ```

  孤儿必须**独立列表**（重算 `folded[:cut]` 在 `cut==0` 时为空，会把循环 append 的孤儿清掉——orphan 来源是 `kept` 不是 `folded[:cut]`）。三场景验算：B→和 3 ✓；C→和 2 ✓；纯孤儿→kept 0 + dropped 1 = 1 ✓。
- **硬要求**：本修复与 P2 的 comp 移除计数**同批落地**（否则 I5 台账断言被旧 bug 污染，"先红后绿"验证对象失真——"事实基础同批"纪律的第三次应用）。

### 落点与纪律

- I1–I3/I5：**测试断言，不做生产守卫**——判定依据是**复杂度匹配**（非成本）：① 修复 P1/P2 后由构造保证，生产校验是"用检查代替构造纪律"；② 真实成本在**失败路径设计与归因**（P3 的病灶正是错误被 engine 边界吞成廉价重试 + `reason=stall` 误归因——为永不触发的检查重开一层失败语义不划算）；③ 避免"复制品义务"。实测成本 0.19ms/732 条（若生产化也无障碍，但归属是复杂度选择）。
- 测试名按 ID（`test_i1_...`/`test_i2_...`）——契约（docstring）↔ 断言（测试名）可 grep 对齐。
- **动机句引用仓内不变量 ID 可核验**（I1–I4 在本仓有定义）；`P0/P15` 式外部编号不可引用——"注释不提编号"规则的可核验边界在此。
- **fixture 断言集**（P2/台账）：① 产物无 compaction 条目（**除非窗口仅含 compaction——保留首条**）；② I2 链连续（桥接后可走、无悬空、链首 `parentId=None`）；③ I4 oracle 集合身份；④ I5 台账闭合；⑤ **反向断言（先红后绿）——fixture 的存在条件**，非可选步骤。退化路径（窗口仅含 comp）必须进 fixture。
- **est 恒等断言撤回**：compaction 条目 `_entry_text` 空 → `_est_tokens` 返 1，移除后 est 必降 `#removed`；"单一测点"已保证 est 反映最终 body。
